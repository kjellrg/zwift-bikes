# Route surface data

Generates real per-route surface composition (% tarmac/gravel/cobbles/brick/
wood/dirt/snow/grass/sand) for every route in `zwift-data`, the same way
[zwiftmap.com](https://zwiftmap.com) computes it: classify a route's real GPS
trace against hand-mapped per-world surface polygons.

This isn't a live app dependency - it's a one-off/periodic data-generation
step. The output is a checked-in JSON file
(`shared/data/routeSurfaces.generated.json`) that the app reads directly;
nothing in `app/`, `server/`, or the Nuxt build runs these scripts.

## How it works

1. **World surface polygons** (`shared/data/zwiftmapSurfacePolygons.json`,
   generated by `extract-surface-polygons.mjs`) - which lat/lng regions of
   each Zwift world are gravel/cobbles/wood/etc., vs. the tarmac default.
   Extracted from zwiftmap's `worldConfigs/*.ts`
   (https://github.com/andipaetzold/zwiftmap, MIT licensed - see
   `/THIRD_PARTY_NOTICES.md`). Only re-run this if zwiftmap updates their
   world surface mapping (new world, new road layout, etc.) - it doesn't
   change often.

2. **Per-route composition** (`shared/data/routeSurfaces.generated.json`,
   generated by `compute-route-surfaces.mjs`) - for each route, fetches its
   real GPS trace from Strava (`route.stravaSegmentId`, already provided by
   `zwift-data`) and classifies each point against the polygons above,
   summing distance per surface type (see `shared/utils/surfaceGeometry.ts`
   for the actual point-classification + aggregation logic, shared with the
   app). The same request also pulls the route's real `altitude` stream and
   simplifies it into `elevationProfile` (see
   `shared/utils/elevationGeometry.ts`) - the dynamic physics model
   (`shared/utils/physics/routeGeometry.ts`) uses this real per-lap elevation
   shape instead of its synthetic named-climb/rolling-lap approximation
   whenever it's available. Re-run this whenever `zwift-data` adds new
   routes, or periodically to catch any Zwift road-surface changes.

   Entries generated before `elevationProfile` was added won't have it until
   re-run with `--force` (see below) - existing routes are otherwise skipped.

   Routes without a `stravaSegmentId` (mostly event-only routes) can't be
   computed this way and are left out - `estimateSurface()` in
   `shared/utils/routeTerrain.ts` falls back to the existing curated/
   heuristic estimate for those.

## Usage

### Re-sync world surface polygons (rare)

```sh
git clone https://github.com/andipaetzold/zwiftmap.git /tmp/zwiftmap
npm run route-surfaces:polygons -- /tmp/zwiftmap
```

### Compute per-route surface composition

Requires a Strava API access token with segment read access:

1. Create an API app at <https://www.strava.com/settings/api>.
2. Complete the OAuth flow for your own account (scope: `read`) to get an
   access token - see
   <https://developers.strava.com/docs/getting-started/#oauth>.
3. Run:

   ```sh
   STRAVA_ACCESS_TOKEN=xxx npm run route-surfaces:compute
   ```

Paced to stay under Strava's ~100 requests/15min rate limit (a full run over
~300 routes takes roughly 45-50 minutes) and backs off automatically on a
429. Safe to interrupt and resume - already-computed routes are skipped on
the next run unless you pass `--force`:

```sh
STRAVA_ACCESS_TOKEN=xxx npm run route-surfaces:compute -- --force
```

Commit the resulting diff to `shared/data/routeSurfaces.generated.json`.
